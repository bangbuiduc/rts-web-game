# RTS Web Game – Isometric

`PROJECT.md` is the source of truth for this project. Update it whenever a product decision, technical decision, milestone, or meaningful implementation status changes. A new session should read this file first and continue from its current status.

## Product

- **Genre:** real-time strategy game inspired by classic Age of Empires.
- **Target:** browser, desktop first; keep the structure compatible with later mobile support.
- **Current goal:** build a playable foundation on an isometric map, then add units, resources, buildings, and RTS systems incrementally.
- **Backend:** none for the initial prototype. Keep gameplay local to the browser.

## Technical decisions

- **Engine:** Phaser 3.
- **Language:** JavaScript (ES modules).
- **Build/dev server:** Vite.
- **Map:** 32 × 32 tiles (1,024 tiles).
- **Tile footprint:** 64 × 32 pixels.
- **Isometric projection:** `screenX = (tileX - tileY) × 32`, `screenY = (tileX + tileY) × 16`, plus a map-origin offset for rendering.
- **Initial art:** programmatically drawn placeholder terrain; replace with authored art later without changing game rules.

## Controls in the prototype

- Move the pointer over the map to inspect a tile and its coordinates.
- The three starting Villagers begin selected so the slice is immediately playable.
- **Left-click** a unit or your Town Center / Barracks to select it; hold **Shift** to add to the selection.
- **Left-drag** on open map to draw a marquee and select multiple units at once.
- **Right-click** issues a context command to the selected units: open ground = move, a tree/berry bush = gather, an enemy unit/building = attack.
- **Right-drag** pans the camera; the **mouse wheel** zooms.
- Press **Escape** to clear the selection (and cancel a pending build placement).
- Use the bottom command bar buttons to train/build; buttons are context-sensitive to the current selection and disable (with a feedback message) when a command is invalid.
- With a Town Center or Barracks selected, **right-click** the map to set its **rally point**: newly trained units walk to that spot, or auto-gather if it is a tree/berry bush. A line and flag mark the active rally point for the selected building.
- A persistent **“⬇ Nhật ký trận (JSON)”** button (top-right) downloads the current match log as a JSON file at any time. It is independent of the context command bar, so it never interferes with the train/build buttons.
- A dismissible **quick-start onboarding card** (bottom-right) shows the objective, the economy→army→assault loop, and the 90 s raid warning on load; it closes via its **×** button or automatically on the player's first issued order (no persistence — it reappears each session by design). A top-center **raid alert** then counts down the final seconds before the Raider push and announces when the push begins.

- **Match logging (current):** added a local, backend-free match logger that records a bounded, time-stamped stream of meaningful gameplay events and can export them to JSON on demand. Pure logic lives in `src/game/matchLog.js`; `scenes/MapScene.js` hooks the events and `ui/commandPanel.js` wires the export button.
  - **Event schema (stable):** every event is `{ seq, type, elapsedMs, data }`. `seq` is a monotonic id (survives ring-buffer eviction so ids stay unique); `elapsedMs` is the **match-elapsed** clock (`MapScene.elapsedMs`), clamped monotonic so a stale delta can never reorder the timeline; wall-clock `createdAt`/`exportedAt` live once on the snapshot envelope (`{ version, createdAt, exportedAt, maxEvents, eventCount, droppedCount, events }`). Event `type`s are frozen in `EVENT_TYPES`: `match-start`, `order`, `resource-delivered`, `node-depleted`, `train-queued`, `unit-trained`, `build-started`, `build-completed`, `enemy-reinforced`, `damage`, `entity-killed`, `victory`, `defeat`.
  - **What is logged (and why not every frame):** events are hooked at decision/transition points — a player right-click order (one event per command with the selected unit ids + target tile/id), a completed resource delivery (not each gather tick), first-time node depletion, training queue/spawn, construction start/finish, each attack connection (`damage`), kills, and the end-game result. Per-frame state (movement steps, hover, enemy retargeting) is deliberately **not** logged. Payloads carry helpful ids, tile positions, and resource snapshots for review.
  - **Bounded buffer:** `createMatchLog({ maxEvents = 2000 })` is a ring buffer; once full it drops the oldest event and counts it in `droppedCount`, so a long match cannot grow memory without bound. A sustained battle is the main source of `damage` volume; the cap is the backstop.
  - **Export:** a persistent top-right button (`#log-export`, outside the context command bar) calls `downloadMatchLog`, which serializes the snapshot, builds a `Blob`, downloads it via a temporary object URL + anchor, then revokes the URL and removes the anchor (no leaks). Filenames are timestamped and filesystem-safe (`rts-match-log-YYYY-MM-DD_HH-MM-SS.json`). No secrets or network calls are involved.
  - **Tests (`test/matchLog.test.js`):** 8 Node tests cover sequence/monotonic-time behaviour, the missing-type guard, ring-buffer eviction + drop counting, snapshot deep-copy isolation, JSON serialization round-trip (pretty vs. compact), filename safety, and the full `downloadMatchLog` lifecycle (Blob build + object-URL cleanup) via injected fakes.
  - **Caveats:** the log lives only in memory for the current page session (no persistence across reload, by design — no backend); the browser-side download glue (`downloadMatchLog`) is validated with injected fakes, not an end-to-end in-browser click.

- **Performance / bundle optimization (current):** replaced the stock full Phaser bundle with a slim, source-built custom entry and split the engine into its own cacheable vendor chunk. The config is `vite.config.js`; the custom entry is `src/game/phaser-slim.js`.
  - **Approach:** Vite now resolves bare `import 'phaser'` (exact match only) to `src/game/phaser-slim.js`, a hand-written entry modelled on Phaser's official `phaser-core` build. Building Phaser *from source* (not the prebuilt `dist/phaser.esm.js` the `module` field points at) lets Rollup tree-shake and lets us exclude whole subsystems the game never uses: the **Arcade + Matter physics engines** (dropped entirely — gameplay uses custom A\* pathfinding), **Sound** (`FEATURE_SOUND=false`; `Game.js` cleanly sets `this.sound = null`), WebGL debug / Spector.js (`WEBGL_DEBUG=false`, which also removes the optional uninstalled `phaser3spectorjs` dep), and the experimental / 3D / Facebook-Instant plugins. Both renderers (Canvas + WebGL) are kept for `Phaser.AUTO`.
  - **Feature flags:** Phaser's source gates these subsystems behind `typeof FLAG` expressions that its own webpack build replaces textually. Vite's `define` can't key on a `typeof X` expression, so the flags are applied in two places sharing one map: a Rollup `transform` plugin for the production build, and an esbuild `onLoad` plugin under `optimizeDeps.esbuildOptions` for the dev dependency pre-bundle (the optimizer does not run Vite `transform` hooks).
  - **Not breaking the game:** stock `phaser-core` omits the Shape (`rectangle`/`ellipse`/`circle`/`triangle`) and `container` Game Objects — which the placeholder art uses heavily — plus `Math.Clamp` and `Math.Distance`. `phaser-slim.js` re-adds exactly those: it imports each Shape/Container class plus their Factory modules (importing a Factory self-registers `scene.add.*` as a side effect) and the two Math helpers. Loader audio file types are omitted (no audio, no asset loading). Missing default-plugins such as `LightsPlugin` are silently skipped by the PluginManager, so their absence is safe.

- **Combat scenario harness (Phase 3, current):** added a deterministic, Phaser-free skirmish simulator so representative matchups can be measured against the *real* combat loop instead of paper DPS math. Pure logic lives in `src/game/skirmish.js`; scenarios/assertions live in `test/skirmish.test.js` (9 Node tests). The harness reuses the shipped modules — `applyDamage`/`tileDistance` (`combat.js`), and `chooseTarget`/`chooseNearestTarget`/`engageableTargets`/`isForceAggressive` (`enemyAI.js`) — and replays `MapScene`'s per-frame semantics: approach until within `attackRange`, a *primed* first strike with no wind-up on a fresh engagement (as `MapScene.onArrive`/`commandAttack` do), then one hit per tick once `attackElapsed` passes `attackCooldown`, plus kill/prune and the garrison guard-radius/aggression stances. It is deterministic (fixed 60 fps dt, stable tie-breaks).
  - **Verified bug fixed — attack-cooldown bypass by click-spam.** `MapScene.commandAttack` (and `onArrive`) set `attackElapsed = attackCooldown` whenever a unit is in range, with no guard against *re-issuing* the attack on the same target already being meleed. Because the enemy AI has a commit check (`updateEnemyAI` skips a still-engageable current target) it was immune, but the **player** was not: every right-click on an adjacent enemy reset the cooldown to "ready", so the next frame fired immediately — rapid clicking let a unit attack every frame (~60×/s) instead of once per `attackCooldown`, inflating player DPS and corrupting any TTK measurement. Fix: a pure `readyToStrikeOnCommand(prevOrder, targetId)` in `combat.js` returns `false` only when the new command *continues* an attack already in its `attacking` phase against the same target; `commandAttack` now primes the first strike only when it returns `true`. A fresh engagement (idle/moving/approaching, or a genuine target switch) still strikes with no wind-up; re-clicking the same meleed target preserves cooldown progress. Covered by `combat.test`-style assertions in `test/skirmish.test.js` and by a harness test showing 1 Clubman vs the Outpost deals exactly 14 damage in 1 s (two hits), not hundreds.

    - **2 vs 4 Clubmen:** attackers wiped in ~1.83 s, **0** enemy kills traded (4 survive). The outnumbered pair never out-trades.
    - **3 vs 4 Clubmen:** attackers wiped in ~4.53 s, trading for **exactly 1** defender (3 survive, one at 13 HP). One extra body converts a shutout into a single trade.
    - **4 vs 4 Clubmen:** decided by *update order*, not stats — the first-listed side wins with 2 survivors (see finding below).
    - **4 Clubmen vs 1 Raider:** Raider dead in ~1.82 s, **0** losses — matches the archived `2026-10-08-victory.json` (first contact 88878 ms → Raider death 90691 ms = **1.81 s**), confirming harness faithfulness.
    - **5 Clubmen vs Outpost + 2 Raiders:** cleared in ~9.0 s with **4** survivors (1 loss). Consistent with the victory log's winnable assault; the paper-math `balance.test.js` estimates Outpost-only TTK in a 3–30 s window.
    - **Delayed/defensive response — 4 Clubmen assault the guarded Outpost:** with the shipped garrison stances (6-tile guard radius, 90 s grace), a force loitering >6 tiles out while calm is ignored; hitting the Outpost latches aggression and the Raiders counter-push, prioritising military. The player still wins the objective (all 3 enemies down in ~16.8 s) but the counter-push is **lethal — 2 of 4 Clubmen fall** (first player death ~6.7 s). Defending the push is a real cost, not a formality.
  - **Finding (not fixed — determinism nuance, no correctness break):** `MapScene.update` processes units in array order and a unit reduced to 0 HP earlier in a tick never retaliates that tick, so a *true mirror* (4 v 4 identical Clubmen in contact) is won by whichever side is listed first (confirmed: reversing the order flips the winner, 2 survivors either way). In the live game enemy Raiders are spawned before player-trained Clubmen, so the tie-break slightly favours the garrison on simultaneous exchanges. This is inherent to sequential resolution and left as-is (no speculative HP/damage change); documented here and asserted in the tests.
  - **Limits:** (1) `MapScene` moves sprites in screen-pixel space (speed is px/s) while range is tiled; the isometric projection makes tile speed direction-dependent, so the harness approximates it with one constant (`SCREEN_PX_PER_TILE`, a cardinal tile step) — approach-phase numbers carry isometric error, so pure-combat TTK is measured in contact and approach figures are indicative. (2) The harness models melee combat only: no pathfinding detours/obstacle avoidance, no gather/economy, no unit collision/stacking, and it uses disciplined focus-fire or the shipped selection policies rather than live mouse micro. (3) HP/damage/speed/radius remain prototype values; these scenarios quantify the *current* tuning and were **not** used to retune it.
- **Outpost reinforcement (Phase 4 P1, current):** added a modest, bounded reinforcement mechanic so a defender who holds the initial 90 s push still faces pressure, without endless spawns. Pure decision logic lives in `src/game/reinforcement.js` (Phaser-free); `scenes/MapScene.js:updateReinforcement` executes it each tick.
  - **Rationale / problem solved:** the previous caveat was that only the two static starting Raiders ever existed, so a player who survived the counter-push with Clubmen was permanently safe and the mid/late game had no tension. Reinforcement closes that gap while staying inside the "modest, no endless spawns" constraint.
  - **Bounds (all three must pass to spawn):** a hard total cap `REINFORCE_MAX = 3` raiders per match (the siege is finite); a minimum `REINFORCE_INTERVAL_MS = 18000` ms between spawns (paced pressure, and a hard floor against frame spam); and a concurrent-force ceiling `REINFORCE_CONCURRENT_MAX = 1` so a reinforcement only *replaces losses* once the garrison is worn down rather than stacking into a swarm. Reinforcement is additionally gated behind an **alive Outpost** and the **aggressive** latch (`enemyAI.isForceAggressive`), so it begins only once the raid is actually on — exactly when a static garrison would have left the defender safe. At most one raider spawns per qualifying tick.
  - **Reuses existing logic:** a reinforcement spawns via the same `addUnit('raider', …, 'enemy')` path as the starting Raiders (placed on a free tile around the Outpost via `freeTileNear`), so it is picked up by `updateEnemyAI`'s target-priority + aggression stances like any other garrison unit — no parallel combat code. ## Simplified mechanics and sources

The slice is *inspired by* the original Age of Empires (Stone Age) but is a heavily simplified, original reimplementation. No Age of Empires code or assets are used; all visuals are placeholder shapes drawn at runtime.

**Verified costs (match AoE1 values):**

- **Villager — 50 Food.** Standard AoE1 villager training cost.
- **Barracks — 125 Wood.** AoE1 Barracks construction cost.
- **Clubman — 50 Food.** AoE1 Clubman (Stone Age Barracks infantry) training cost.

These three costs are defined in `src/game/rules.js` and were checked against [Age of Empires Heaven's Villagers](https://aoe.heavengames.com/theacademy/unitsboatsandbuildings/villagers/), [Barracks](https://aoe.heavengames.com/theacademy/unitsboatsandbuildings/barracks/), and [Clubman](https://aoe.heavengames.com/theacademy/unitsboatsandbuildings/clubman/) pages; [Artho's original-era building guide](https://artho.com/age/buildings2.html) independently lists Barracks at 125. All other numbers (HP, attack, speed, train/build times, resource node amounts, population cap) are prototype values chosen for playability, **not** AoE1-accurate. An initial balance pass has tuned the resource node amounts and the train/build times (see the "Balance pass" entry under *Current implementation status*); HP/damage were reviewed and left as-is for now.

**Deliberate simplifications vs. AoE1:**

- Only two resources (Food, Wood); no Gold/Stone, no farming, no age advancement or tech tree.
- A single building footprint is one tile; no terrain elevation, no fog of war, no line-of-sight reveal.
- Gathering is a fixed one-unit-per-tick loop with a small carry capacity rather than per-resource gather rates; the Town Center accepts both resources so no separate Granary/Storage Pit drop-off is required in the slice.
- Combat is single-target melee with a flat damage value and cooldown; no armor, no ranged units, no projectiles, no attack-move or formations.
- Enemy AI is a reactive garrison, not a strategic opponent: it has target priorities and a two-stance aggression model (see the "Enemy AI" entry under *Current implementation status*) but still has no base-building, scouting, or resource economy.
- Population is capped by buildings that provide population (the Town Center provides 8); Houses exist in the rules data but are not part of the current slice.

## Save-game vs. multiplayer feasibility

Concrete architecture assessment written during the Phase 5 pass. **Nothing here is implemented** — no backend, save system, or netcode exists. The point is to record the shortest credible path to each, and the shared prerequisite.

### Current state model (the thing both features serialize/replicate)

The authoritative game state already lives as **plain data on `MapScene`**, separate from rendering: `units[]`, `buildings[]`, `nodes[]`, `resources`, `elapsedMs`, `enemyAggressive`, `reinforcementsSpawned`, `lastReinforceMs`, `nextId`, `selectedIds`, `pendingBuild`, `gameOver`. Each entity is a POJO (`id`, `type`, `faction`, `tile`, `hp`, `order`, `path`, `carried`, `queue`, `rally`, stats…) plus a non-serializable `visual` (Phaser container) and the live screen position on `visual.container.x/y`. Crucially, the gameplay *rules* already live in **Phaser-free pure modules** (`combat`, `economy`, `enemyAI`, `reinforcement`, `resourceLoop`, `rally`, `pathfinding`, `selection`, `guidance`) that run under Node in the test suite — so the simulation logic is already reusable outside the browser.

### Save-game — feasible now, low complexity, no backend

- **Approach:** add a `src/game/saveState.js` with `serializeState(scene)` → a POJO snapshot (entities minus their `visual`/function refs; include **both** `tile` and `container.x/y` so an in-flight unit restores without snapping) and `restoreState(scene, snapshot)` that rebuilds visuals through the **existing** `addUnit`/`addBuilding`/`addNode` factories (they already construct art from data) then re-applies `hp`/`order`/`queue`/`resources`/clocks/`nextId`.
- **Storage:** single-slot `localStorage` JSON, or a downloadable `.sav` JSON reusing the match-log download glue (`downloadMatchLog`'s Blob/object-URL pattern). State is bounded (a few hundred entities), so size is trivial.
- **Effort:** ~1 module + a save/load button. The hard part — separating serializable state from Phaser handles — is already most of the way done because logic is Phaser-free and the scene holds data arrays.
- **Risks / caveats:** cosmetic timers (`this.time.delayedCall` for raid-alert clearing) are dropped on load and re-derived from `elapsedMs`; the match-log stream either resets or is snapshotted alongside; version the snapshot envelope so format changes don't crash old saves. No determinism requirement (single client).

### Multiplayer — needs a backend; two architectures

1. **Deterministic lockstep (send only commands/inputs — classic AoE model).** Lowest bandwidth, scales to many units. **Blocked by determinism today:** movement integrates `unit.speed * delta/1000` in floating-point *screen pixels* with a variable frame `dt` (`MapScene.stepAlongPath`), and resolution order depends on array order — floats and frame timing diverge across machines/browsers, so two clients would desync. Adopting lockstep requires: a **fixed-timestep simulation tick decoupled from render**, tile-space or fixed-point movement, deterministic iteration/tie-breaks, a **seeded PRNG** for any future randomness, and command scheduling with input delay. The pure rule modules are already deterministic and reusable; the update *loop* is what needs the rewrite.
2. **Authoritative server with state sync.** The server runs the sim (reuse the Node-friendly pure modules in a headless scene loop) and broadcasts state snapshots/deltas; clients render and send intents. Tolerant of non-determinism, lower refactor risk to the sim, but needs a Node + WebSocket server, client-side interpolation, and basic anti-cheat/validation.
- **Recommendation:** for a 1v1 versus/co-op of this slice, the **authoritative-server + periodic state-sync** path is the pragmatic first step — it reuses the existing pure logic and avoids the determinism rewrite. **Lockstep** is the better long-term fit for large unit counts but is gated on the fixed-timestep refactor. Both require a backend and are **out of scope for the local prototype**.
- **Shared prerequisite (do this first):** split **simulation from rendering** — a fixed-step `update(state, dt)` over POJO state, with Phaser as a pure view. That single refactor is what *both* save-game (clean snapshot boundary) and multiplayer (deterministic/headless sim) need, so implementing save-game first naturally de-risks multiplayer.
